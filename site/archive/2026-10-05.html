Đọc bài gốc

RemoveMacAI is a command-line tool on GitHub that turns off Apple Intelligence features on macOS 27, removes the downloaded models and stops macOS from downloading them again. Per the README, macOS 27 no longer has a single switch for Apple Intelligence, and its models stay on disk after the features are turned off.

Usage:
- Install with a curl ... | bash one-liner (the script downloads the latest release, verifies its SHA-256 checksum and runs from a temporary directory, installing nothing) or with Homebrew: brew install omlahore/tap/removemacai.
- removemacai shows the current state, then turns Apple Intelligence off; status lists each feature and model size; off --keep leaves chosen features on; off --dry-run previews; revert undoes everything.

It turns off Siri (including "Hey Siri"), Writing Tools, Genmoji, Image Playground, the ChatGPT extension, summaries in Mail, Messages, Safari, Notes and notifications, Mail smart replies, Photos Clean Up and Xcode predictive code completion.

How it works: a configuration profile applies Apple's restriction keys; models are removed through Apple's asset service, System Integrity Protection stays enabled and nothing under /System is modified directly; the profile redirects each removed model's download to a closed local port so macOS does not fetch it again. macOS requires the user to approve the profile in System Settings. macOS updates do not undo the changes.

Limits: Apple silicon and macOS 27 only (tested on 27.0; on 27.0.1 use 0.2.3 or later). Apps that use Apple's on-device models (the Foundation Models framework, the Use Model action in Shortcuts) stop working. Dictation still works. The tool says it makes no network requests and collects no data.

The reports come from Governor Jim Pillen's July 20 executive order requiring data centers to self-report their impact on water, power grids and local infrastructure; reports were due Sept. 30. 10/11 filed a public record request to see the redacted information.

Đọc bài gốc

mabl's engineering team cut its pull request gate from 288 candidate tests to 17, choosing tests from real usage data, ranking journeys by failure impact, and eliminating flakiness so the gate is believable again.

The problem: once a gate goes red and nobody believes it, developers rerun, override, and route around it. With coding agents shipping more changes, the pre-merge check has to be independent of the agent that wrote the change and has to be trusted.

How they did it:
- Journeys first, tests second: they looked at 30 days of real usage and kept the set small but thorough.
- Three tiers by failure impact: Tier 1 means the customer can't build, edit, or run tests, or results are wrong; Tier 2 means lost time and a workaround; Tier 3 means the customer notices but isn't blocked. When instinct and data disagreed, the tiers followed the data.
- Four questions per journey, all yes to qualify: covered on the surface the customer uses, does that coverage run, does it check the outcome, is it proportionate to the tier. An enabled test that hasn't executed in 90 days isn't coverage.
- Checking the outcome means proving it held through a save, a backend run, or a full round trip: a changed credential reaches the runtime, a failed run is reported as failed.

Why 17: the gate blocks a merge if any test fails, so failure rates multiply. At 99% reliability per test, a 17-test gate passes cleanly about 84% of the time, a 288-test gate about 5%. You widen a gate by fixing tests, not adding them. A coding agent produced the 288-test list on its first pass and was fast at mapping tests to journeys; deciding what the gate is for was the team's job.

Everything else still runs after merge: roughly 240 UI tests plus the API suite. The gate deliberately leaves out tests that query a third-party tracker (so someone else's outage can't block merges) and Trainer recording tests (which have their own suite). Even 84% isn't enough, since about three in 20 PRs would fail for no reason, so they set the goal on the whole gate and spent months eliminating flaky tests.

Đọc bài gốc

The author built AdversaryGate, a tool that runs your tests and returns one of three answers, to catch patches that look verified: a test that passed because it never ran, coverage that cleared the floor because the number was an unmeasured default, or an agent that introduced a bug and rewrote the assertion to agree with it.

Three answers:
- Exit 0, MERGE: every claim executed and cleared the floors.
- Exit 1, BLOCK: something that passed before fails now.
- Exit 2, INCONCLUSIVE: something wasn't measured, so it doesn't become a green check. A measurement nobody produced can't clear a floor.

The case that started it: an agent changes add to return a + b + 1, then edits the test to expect 6 instead of 5, and the patch's own tests pass. AdversaryGate notices the patch changed a test the baseline already had, puts back the baseline's copy of the tests (helpers included), runs them against the new code, and BLOCKs because the test passes on baseline and fails on patch.

What it measures:
- The same tests on both sides (named, or picked by coverage.py's per-test contexts as the tests that executed the changed lines). Only a real test failure counts as evidence; import errors, missing tests, timeouts and runs killed by resource limits are unverified, not failed.
- Diff coverage computed from the unified diff and the coverage.py JSON report, test files excluded; both inputs are recorded by SHA-256.
- Mutation testing on the lines the patch wrote, one mutant per changed line before any line gets a second. The floor reads the lower bound of an 80% Wilson interval rather than the raw ratio: 1/1 killed gives 0.378, 4/4 gives 0.709 (neither clears 0.75), 5/5 gives 0.753 (clears).
- The full suite on both sides; passing on baseline and failing on patch is a collateral regression, BLOCK. A passing claim also says how it passed: fixed or no_regression.

The patch can't configure its judge: a patch could ship a .pytest.ini with addopts and a plugin that reported passed only while the source had the exact bytes of the bug, producing MERGE with add(2, 3) == 6. Now every test-harness file (all five config names pytest 9 reads, conftest.py, sitecustomize.py, *.pth) must be byte-for-byte the baseline's. That finding and 31 others are in a public ledger.

MCP: since 2.8 it ships an MCP server so an agent can call the gate before saying done. The design rule: the agent says what to judge; whoever runs the agent says how strictly, through ADVERSARY_GATE_POLICY, ADVERSARY_GATE_BASE_REF and ADVERSARY_GATE_PYTHON. There is also a GitHub Action that takes base-sha.

Đọc bài gốc

Specumber provides SpecFlow-style bindings for Cucumber (cucumber-js): step definitions and hooks are methods of a class, and the class holds the state of a scenario. It is inspired by Tim Roberts' cucumber-js-tsflow and presented as a modern drop-in replacement that passes the original project's test suite.

Usage:
- @binding() marks a class Cucumber should know about; the steps and hooks on it are registered when the class is declared. A decorated method in a class without @binding() is never run.

- Cucumber's own --loader will not work with tsx.
- No tsconfig.json change is needed: the decorators work under both the standard TypeScript 5 proposal and experimentalDecorators.

- Golden set: file JSON/JSONL cạnh prompt, mỗi lỗi production được sửa thành thêm một dòng; dùng case thật (tin rỗng, tin tiếng Ả Rập, tin chỉ là số order, prompt injection dán từ email) hơn là case tổng hợp; để prompt trong file riêng để thay đổi prompt và kết quả eval nằm chung một diff.
- Assertion tất định (Zod schema, chuỗi bắt buộc/cấm, khoảng số) bắt phần lớn regression, chạy trong mili giây và không tốn tiền; chạy chúng trước.

Đọc bài gốc

An LLM feature cannot be unit-tested with string equality because the same prompt returns different text on every call, so the author asserts on properties of the output. Three changes made their AI features safe to refactor: a version-controlled golden set of real inputs, deterministic assertions running before any LLM-as-judge call, and a CI gate on pass-rate regression rather than a perfect score.

The story: a route turning free-text support messages into structured tickets worked fine. Weeks later a colleague changed the wording of the tone instructions in the system prompt and extraction started inventing order IDs for messages with none. Every test still passed because the only tests covered the code around the model.

Key points:
- An eval runs a prompt against fixed inputs and scores output on properties instead of exact text, replacing toEqual.
- temperature: 0 makes output more stable but not byte-identical because providers batch requests; exact-string tests are red on Tuesday and green on Wednesday.
- Split the code at the model boundary: prompt assembly, retry logic, output parsing and tool dispatch are deterministic and get ordinary unit tests; only the model call needs an eval. Properties to check: parses against the schema, stays in the requested language, cites only identifiers present in the input, refuses when context has no answer, never echoes the system prompt.
- Golden set: a JSON/JSONL file next to the prompt; every production bug fixed becomes another row. Prefer real awkward cases (the empty message, one in Arabic, one that is only an order number, a prompt injection pasted from an email) over synthetic ones, and keep the prompt in its own file so prompt changes and eval results share a diff.
- Deterministic assertions (Zod schema, required and forbidden strings, numeric ranges) catch most regressions in milliseconds at no cost; run them before any judge call.
- LLM-as-judge is a second model call scoring output against a rubric; it is trustworthy only with a pinned model ID, binary rubric questions and verdicts compared against human labels.
- Gate CI on regression: fail when the pass rate drops below a baseline committed to the repo, and make raising the baseline a reviewed commit.

Assert rằng LLM trả đúng một chuỗi chắc chắn là một flaky test: LLM ánh xạ một input sang một phân phối các output hợp lý, và provider không đảm bảo output tất định ngay cả với fixed seed và temperature zero. Cách đúng là kiểm tra thuộc tính của kết quả và xây eval set thay vì chỉ unit test.

Mutation Testing: Why full coverage proves nothing 100% coverage không nói lên nhiều; mutation testing cài lỗi vào code rồi kiểm tra test có bắt được không. Điều này quan trọng hơn khi AI viết test.100 % Coverage heißt wenig. Mutation Testing baut Fehler in deinen Code und prüft, ob deine Tests sie finden. Das zählt, sobald KI Tests schreibt.

Bài từ podcast Software Testing (Richard Seidl, 29. Sept. 2026, bằng tiếng Đức) giải thích rằng mutation testing, tức cố ý cài lỗi vào production code rồi xem test có bắt được không, đo chất lượng test suite tốt hơn code coverage, nhất là khi agent AI viết test.

  • Code coverage đo việc chạy qua code, không đo việc kiểm tra. Thí nghiệm tư duy: hệ thống có 100% coverage (line hay branch); xóa hết assertion khỏi test thì coverage vẫn giữ nguyên, trong khi test đã vô dụng. Có thể "ăn gian" coverage bằng cách chạy code mà không kiểm tra kết quả.
  • Cách hoạt động: tool chạy toàn bộ test để biết code nào được bao phủ, nhớ test nào phủ dòng nào, rồi biến đổi production code (đổi "kleiner gleich" thành "kleiner", phủ định điều kiện trong if), chỉ chạy lại các test phủ dòng đã đổi. Test fail nghĩa là mutation bị "killed"; mọi test vẫn xanh nghĩa là mutation "survived". Mutation coverage là tỷ lệ mutation bị killed. Ở đây test xanh là kết quả xấu: "Wenn diese Tests danach immer noch grün sind, ist es schlecht." (Julius Mischok)
  • Các mutator điển hình: dịch ranh giới (> thành >=), đảo so sánh (> thành <), phủ định bằng (== thành !=), phủ định điều kiện (if (x) thành if (!x)), lật boolean, và trả về giá trị mặc định (0, false, list hoặc set rỗng). Mutator giá trị mặc định giả vờ phương thức không làm gì; nếu không test nào phát hiện thì không ai kiểm tra kết quả. Mutator ranh giới trùng với phân tích giá trị biên; mutation sống sót thường nghĩa là thiếu dữ liệu test đúng tại biên.
  • Yêu cầu: test phải cô lập và ổn định, vì tool chạy lại theo thứ tự tùy ý và một phụ thuộc giữa các test làm cả quy trình hỏng.
  • Julius Mischok, người dùng mutation testing trong hệ Java, nói khái niệm này đã có gần 20 năm, nhưng đang quay lại vì AI agent viết ngày càng nhiều test. Gợi ý: chạy job theo lịch hằng tuần hoặc cuối sprint để biết test do AI sinh có thật sự bắt lỗi.

Đọc bài gốc

This podcast article (Software Testing, Richard Seidl, 29. Sept. 2026, in German) explains that mutation testing, which deliberately builds faults into production code and checks whether the tests find them, measures test-suite quality better than code coverage, especially when AI agents write the tests.

  • Code coverage measures execution, not verification. A thought experiment: a system has 100 percent coverage (line or branch); remove all assertions from the tests and coverage stays the same, though the tests are now worthless. Teams can game coverage by running code without checking any result.
  • How it works: the tool runs all tests to learn which production code is covered, remembers which test covers which line, then mutates the code (turning "less or equal" into "less", negating the condition in an if) and reruns only the tests covering the mutated line. If a test fails, the mutation is "killed"; if all stay green, it "survived". Mutation coverage is the share of killed mutations. Here a green test is the bad result: "Wenn diese Tests danach immer noch grün sind, ist es schlecht." (Julius Mischok)
  • Typical mutators: shift a boundary (> to >=), flip a comparison (> to <), negate equality (== to !=), negate a condition (if (x) to if (!x)), flip booleans, and return a default value (0, false, an empty list or set). The default-value mutator pretends the method does nothing; if no test notices, nobody checks the result. Boundary mutators match classic boundary value analysis; a surviving one usually means missing test data exactly at the boundary.
  • Requirement: tests must be isolated and stable, because the tool reruns them in any order and a single dependency between tests makes the process fail.
  • Julius Mischok, who uses mutation testing in the Java world, says the concepts have existed for almost 20 years, but it is gaining relevance because AI agents write more and more tests. The suggestion: a weekly scheduled job or a run at sprint end shows whether the generated tests really find faults.
