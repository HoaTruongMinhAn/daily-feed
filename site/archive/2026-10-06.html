Fixing the Verification Gap in the AI-Native SDLC mabl phê bình playbook AI-Native SDLC của Anthropic vì giả định trạng thái đúng của ứng dụng đã cố định, nên không có cách cập nhật test khi yêu cầu thay đổi có chủ đích.mabl critiques Anthropic's AI-Native SDLC playbook for assuming the verified state is settled, leaving no way to update test coverage when requirements change on purpose.

Geoff Cooney phê bình playbook AI-Native SDLC của Anthropic: cả hai cơ chế kiểm tra ở giai đoạn test đều giả định trạng thái đúng của ứng dụng đã cố định, nên không có cách cập nhật test khi yêu cầu thay đổi có chủ đích, và cuối cùng coding agent tự quyết định "đúng" là gì.

Playbook chia SDLC thành vòng lặp sáu giai đoạn (plan, design, build, test, deploy, maintain), mỗi giai đoạn chốt một artifact (intent.md, spec.md, plan.md, diff cùng test, PR, incident record). Giai đoạn test có hai kiểm tra:
- Feedback loop: mỗi phiên agent tự kiểm tra việc của mình bằng test, build hoặc so screenshot. CLAUDE.md mẫu ghi "If a test fails, fix the code, not the test." Một verifier subagent có thể chạy kiểm tra cuối trong context mới.
- Continuous evals: bộ 20 đến 50 tác vụ thật chạy mỗi khi cấu hình hay model của agent đổi, để xác nhận agent vẫn làm việc đúng chuẩn.

Các điểm tác giả chỉ ra:
- Tính năng mới: độ phủ test chỉ đến từ cách agent tự đọc thay đổi lúc viết code. Thiếu bước biến intent.md và spec.md thành test case mà doanh nghiệp sở hữu. Với ứng dụng quan trọng (ví dụ ngành chịu quản lý của FDA), test là bằng chứng, và kiểm toán sẽ hỏi test nào phủ yêu cầu nào, ai duyệt khi nó đổi.
- Hành vi cũ: "fix the code, not the test" đúng khi sửa bug, nhưng mẫu CLAUDE.md áp nó cho mọi thay đổi. Khi sản phẩm đổi có chủ đích, kết quả đúng của hôm qua thành lỗi hôm nay. Một test hỏng theo hai cách: hành vi đổi có chủ đích (test cần cập nhật kỳ vọng) hoặc cách thực thi đổi (nút dời chỗ, form tách hai màn hình, đăng nhập qua identity provider mới; ý định test giữ nguyên, cách chạy phải đổi).
- Bộ eval chỉ lớn thêm, không case nào được sửa khi yêu cầu đằng sau nó thay đổi.

Kết luận của tác giả: thiếu một đường và một artifact, tức cách xác định độ phủ test mà thay đổi cần, và phán quyết độc lập về việc ứng dụng còn đúng ý đồ kinh doanh hay không. Phần sau của bài không nằm trong đoạn trích.

Đọc bài gốc

Geoff Cooney critiques Anthropic's AI-Native SDLC playbook: both checks in its testing stage assume the verified state of the application is already settled, so nothing covers updating tests when requirements change on purpose, and the coding agent ends up deciding what "correct" means.

The playbook models the SDLC as a loop of six stages (plan, design, build, test, deploy, maintain), each ending by committing an artifact (intent.md, spec.md, plan.md, the diff and its tests, the PR, the incident record). The testing stage has two checks:
- Feedback loop: each session checks its own work with tests, a build or a screenshot diff. The sample CLAUDE.md says "If a test fails, fix the code, not the test." A verifier subagent can run the final check in a fresh context window.
- Continuous evals: a suite of 20 to 50 real tasks runs whenever the agent's configuration or model changes, to confirm the agent still works to the same standard.

The author's points:
- New features: coverage comes only from the agent's own reading of the change while it builds. No step turns intent.md and spec.md into test cases the business owns. For business-critical apps (for example FDA-regulated industries) a test case is evidence, and auditors will ask which requirement each test covers and who approved it when it changed.
- Existing behavior: "fix the code, not the test" is right for a bug fix, but the sample CLAUDE.md applies it to every change. When the product changes on purpose, yesterday's correct result becomes today's failure. A test breaks in one of two ways: the behavior changed on purpose (the expected result must adapt) or the execution changed (a button moves, a form splits across two screens, login goes through a new identity provider; the intent stays, the way it runs must change).
- The eval suite grows, but no case is ever revised after the requirements behind it move.

The author's conclusion: the loop is missing one path and one artifact, an AI-native way to identify the test coverage a change needs, and an independent verdict on whether the application still does what the business intends. The rest of the article is beyond the excerpt.

Cloudflare ra mắt bản beta Web Search API (ngày 2 tháng 10, 2026), cho phép AI agent và ứng dụng tìm kiếm Internet và neo câu trả lời vào thông tin trực tiếp thay vì đoán URL hay dựa vào mốc training cutoff của model.

  • Lúc ra mắt có ba nhà cung cấp tìm kiếm: Ceramic.ai, Exa và Linkup. Cả ba hỗ trợ Zero Data Retention với request đi qua Cloudflare và cam kết theo chuẩn verified bot crawling của Cloudflare.
  • Chạy qua AI Gateway: request hiện trong gateway logs và tính vào AI Gateway credits theo giá niêm yết của từng nhà cung cấp, không phụ phí. Có thể dùng API key của riêng bạn.
  • Gọi bằng REST (POST tới /ai/websearch/ với query, provider, limit, options.gateway.id) hoặc từ Worker bằng binding AI: env.AI.websearch({ gatewayId, query, provider, limit }).

Với người xây sản phẩm AI: đây là cách thêm search cho agent mà vẫn có log và billing tập trung ở một chỗ. Hướng dẫn chi tiết nằm ở trang "How to use Web Search API".

Đọc bài gốc

Cloudflare announced Web Search API in beta (October 2, 2026). It lets AI agents and applications search the Internet and ground responses in live information, instead of guessing URLs or relying on a model's training cutoff.

  • At launch there are three search providers: Ceramic.ai, Exa and Linkup. All three support Zero Data Retention for requests made through Cloudflare and have committed to Cloudflare's verified bot crawling standards.
  • It runs through AI Gateway: requests show up in gateway logs and are billed to AI Gateway credits at each provider's list API price, with no additional markup. You can also bring your own provider API key.
  • Call it with the REST API (POST to /ai/websearch/ with query, provider, limit and options.gateway.id) or from a Worker with the AI binding: env.AI.websearch({ gatewayId, query, provider, limit }).

For people building AI products: a way to add search to an agent while keeping logs and billing in one place. The full guide is on the "How to use Web Search API" page.

Đọc bài gốc

Reflection introduced Beam, its first open-weight model: a sparse Mixture-of-Experts with 501 billion total parameters and 23 billion active, built for coding, reasoning and agentic workloads. Beam is in final red-teaming and evaluation; the company says it will release weights, technical report, model card and developer artifacts later this month, and for now only early-access sign-up is offered.

  • Pretraining: 23.8 trillion tokens from the web and proprietary licensed datasets, which the company says matches or outperforms available similar-sized open base models.
  • High-compute RL: over 100 million rollouts on 10.5K NVIDIA GB300 GPUs across 4 weeks, with a maximum context length of 256K.
  • Claimed position: advances the Western open-weight frontier, competitive with GLM 5.2 and approaching Qwen 3.8-Max on coding and agentic tasks. Kimi K3 remains ahead on raw capability; Beam's advantage is inference efficiency.

  • Efficiency: reasoning scores comparable to GLM-5.2 with 3-4x less inference compute; the estimate uses FLOPs ≈ 2 × active parameters × mean generated tokens, excluding prefill and serving overhead, so it is approximate.

Caveat: all figures are the company's own and the weights are not yet released.

Pi, coding agent của Mario Zechner, nay có MCP tích hợp sẵn, nhưng không đưa toàn bộ định nghĩa tool của server vào prompt: nó dùng Codemode để tìm tool khi cần, gọi chúng từ JavaScript và chỉ trả về phần đầu ra hữu ích.

  • Vấn đề: Zechner đo thấy riêng Chrome DevTools MCP chiếm khoảng 18.000 token, tức khoảng 9% context 200.000 token, trước khi agent làm gì. Playwright MCP cần khoảng 13.700 token cho 21 tool (6,8%). Ông cũng chê MCP không composable: kết quả phải đi qua context của agent mới lưu ra đĩa hay kết hợp được.
  • Cách cũ: dùng Bash và vài script; README của công cụ trình duyệt CLI chỉ 225 token, đầu ra có thể pipe, lọc, lưu mà không qua model.
  • Cách mới: Codemode chạy trong sandbox QuickJS, không có Node API, file system, network hay timer. Script gọi tool và model của Pi, chạy đồng thời và xử lý kết quả trước khi trả lại model. Mặc định prompt hệ thống chỉ có mô tả một dòng cho mỗi server.
  • Tinh chỉnh: toolExposure cho phép lộ một số tool trực tiếp, để số khác sau Codemode, hoặc chặn hẳn (ví dụ lộ search_code, giấu get_*, chặn delete_*). Ngân sách mặc định 3.000 token cho khai báo tool; phần vượt vẫn tìm được.
  • Pi 1.0 giảm cả dấu chân của Codemode: theo release notes, một request GPT-5.6 với tool mặc định giảm từ khoảng 5.300 xuống 3.300 token prompt.

Hạn chế: Pi 1.0 không giải quyết hết phàn nàn của Earendil về MCP, gồm composability.

Đọc bài gốc

Pi, Mario Zechner's coding agent, now has MCP built in, but it does not put all of a server's tool definitions in the prompt: it uses Codemode to find tools as needed, call them from JavaScript and return only the useful output.

  • The problem: Zechner measured Chrome DevTools MCP alone at roughly 18,000 tokens, about 9% of a 200,000-token window, before the agent had done anything. Playwright MCP needed about 13,700 tokens for 21 tools (6.8%). He also argued MCP isn't composable: results must pass through the agent's context to be saved to disk or combined.
  • The old answer: Bash and a few scripts; the CLI browser tools needed only a 225-token README, and output could be piped, filtered or saved without passing through the model.
  • The new approach: Codemode runs in a QuickJS sandbox with no Node APIs, file system, network or timers. Scripts call Pi's tools and models, run concurrently and process results before returning anything to the model. By default the system prompt gets a one-line description per server.
  • Tuning: toolExposure can expose some tools directly, leave others behind Codemode or block them (for example expose search_code, keep get_* behind Codemode, block delete_*). Codemode has a 3,000-token default budget for tool declarations; the rest stays discoverable.
  • Pi 1.0 also shrank Codemode's footprint: per the release notes, a GPT-5.6 request with default tools fell from roughly 5,300 to 3,300 prompt tokens.

Caveat: Pi 1.0 doesn't resolve all of Earendil's complaints about MCP, including composability.

Simon Willison trích Felix Rieseberg mô tả hai kiến trúc của Cowork: bản "cũ" chạy suy luận trên cloud nhưng thực thi tool trong một VM do Anthropic cung cấp trên máy người dùng, còn bản "mới" chuyển cả suy luận lẫn VM lên cloud.

  • Bản cũ: VM được thêm vì khả năng, an toàn và bảo mật, chỉ ánh xạ vào dữ liệu người dùng thêm rõ ràng vào phiên. Người dùng thích những gì Claude làm được nhưng không thích chi phí đĩa, pin và hiệu năng của VM chạy cục bộ, và việc đóng laptop thì công việc dừng.
  • Bản mới: mỗi phiên có sandbox riêng, không chia sẻ trạng thái với phiên khác. Khi VM cần thứ gì trên thiết bị (như một file), ứng dụng desktop chịu trách nhiệm cho tool call truy cập file đó.
  • Anh ta cho rằng cách này giải quyết nhiều vấn đề đã nghe: dùng Cowork từ điện thoại, giữ công việc tiếp tục chạy, và có cùng sức mạnh mà không hao pin vì VM.

Nguồn chỉ là một đoạn trích ngắn; chi tiết khác nằm ở bản gốc.

Đọc bài gốc

Simon Willison quotes Felix Rieseberg on the two Cowork architectures: the "old" one runs model inference in the cloud but executes tool calls in an Anthropic-provided VM shipped to your computer, while the "new" one moves both inference and the VM to the cloud.

  • Old version: the VM was added for capability, safety and security reasons, mapping in just the data you explicitly added to a session. People loved what Claude could do but not the disk, battery and performance cost of running the VM locally, and closing the laptop stopped the work.
  • New version: each session gets its own sandbox, not sharing state with other sessions. When the VM needs something on the user's device (like a file), the desktop app is responsible for that file access tool call.
  • The quoted author thinks this solves many problems they've heard about: using Cowork from a phone, keeping work running, and getting the same power without losing battery to the VM.

Ephemeral testing: checking software through throwaway AI-built layers

Daniel Lemire proposes "ephemeral testing": instead of assessing your component directly, you ask an AI agent to build an application or another layer on top of it, have it test what it built, and assess how good that software is. The software on top is thrown away when you are done.

Key points:
- It is a form of integration testing; the difference is that the layer on top is entirely ephemeral.
- A library with a clean API, stable invariants and useful errors lets the agent produce something that works quickly. One with hidden state, surprising defaults or incomplete docs produces a pile of patches and failures. Those failures are evidence about your code, not about the agent.
- You can repeat it with different agents and tasks on the same foundation.

  • Cause: the connectedAccounts query on the /metadata GraphQL API returned connection details for every account in a workspace, including the passwords of IMAP, SMTP and CalDAV accounts. No exploitation in the wild or public proof-of-concept is confirmed.

- Upgrade to Twenty 2.7.0 or later. The fix hides the field, scopes lookups to the caller and encrypts credentials at rest. The upgrade is a breaking change for connected account storage, so read the release notes first.
- Treat every IMAP, SMTP or CalDAV password entered into an affected workspace as compromised and rotate it at the mail provider, especially where untrusted members had access.

qlabs presents Dust, which it calls the first zeroth-order method that is competitive with backprop at pretraining transformer language models.

  • How it works: Dust perturbs activations (node perturbation) independently at every token, so each token is a virtual population member and one forward pass evaluates them all in parallel. It rewards each perturbation by how much it lowers the loss and averages the reward-weighted perturbations over a population to estimate the gradient.
  • At large population (substantially more compute), Dust approximates backprop closely and in multiple settings even exceeds it. The team suggests that in a compute-rich regime it might surpass backprop.
  • Efficiency: based on the team's extrapolations, from 1M tokens up Dust is on the order of 10^3 to 10^4 times more efficient than a transformer implementation of EGGROLL, a state-of-the-art ES method that perturbs weights.
  • The surprise: zeroth-order methods are widely believed not to scale, yet here larger models are more population-efficient, with a 243M-parameter model outperforming a 120x smaller model at most population sizes. Gradient estimates align better with backprop as population grows and stay well aligned at every scale tested, up to 1B tokens.
  • Motivation: following the bitter lesson that general methods that scale with compute eventually win, they aim to replace backprop with an algorithm built on brute-force search rather than analytic structure.

Đọc bài gốc

Derek Comartin argues that multi-tenant best practices do not remove complexity, they only relocate it, and illustrates it with a real bug.

The bug: an HTTP API places a message on a queue to generate an invoice and a background process picks it up. There were no exceptions, no failed database calls and no errors in the logs, but a request meant for tenant A executed for tenant B.

The cause: the team chose not to pass the tenant ID everywhere and built an implicit context instead. But the context of an HTTP request and the context of processing a queue message in a background process are completely different, so the context has to be rebuilt from the message. Getting that wrong produces the bug.

  • Explicit tenant identity: the tenant ID travels with every request, message, log and database operation. It is noisy but visible, and you are forced to deal with the dependency.
  • Implicit tenant context: simpler APIs and less plumbing, but a hidden dependency; the context must exist and be rebuilt whenever you move between execution contexts.
  • Other recommendations such as global query filters, a database per tenant and feature flags are not bad, but they often leave out the tradeoff and the cost.

The better question is not "what is the right way to build a multi-tenant system?" but "what are the tradeoffs of my decisions and where am I putting the complexity?" Tác giả tự dựng một file tar từ spec POSIX bằng struct của Python và phát hiện: đổi một byte nội dung thì tar vẫn giải nén với exit code 0, còn đổi một byte ở header thì tar từ chối.

  • Cấu trúc: chuỗi các block 512 byte. Mỗi file có một block header, rồi nội dung đệm tới bội số của 512, kết thúc bằng hai block toàn số 0. Không có magic number, không có mục lục. Hầu hết số trong header được ghi dưới dạng chữ số octal ASCII. Hai file như vậy cho ra 3,072 byte và GNU tar 1.35 đọc được bình thường.
  • Checksum: chỉ là tổng 512 byte của header, không phải CRC hay hash, và chỉ bao header. Đổi "first file" thành "Xirst file" trong nội dung: exit code 0, file hỏng nằm trên đĩa. Đổi chữ cái đầu tên file trong header: tar báo "This does not look like a tar archive" và thoát với lỗi. Checksum sinh ra để ổ băng nhận ra block header và đồng bộ lại sau lỗi đọc, không phải để bạn tin dữ liệu. Một file .tar trần không có bảo đảm toàn vẹn; .tar.gz được bảo vệ nhờ gzip/xz chứ không phải nhờ tar.
  • Giới hạn octal: trường size có 11 chữ số octal, tối đa 8,589,934,591, thiếu một byte so với 8 GiB. Với file sparse 9 GiB, ustar từ chối, định dạng GNU đặt bit cao để chuyển sang số nhị phân, còn pax thêm header phụ ghi size thập phân không giới hạn.
  • Không có index: muốn tìm một file phải đi từ đầu, nhảy theo size từng header. Với 2,000 file 50 KB (khoảng 100 MB), trích file cuối của tar không nén cần 2,001 lần seek và 34 ms, còn ZIP cần 7 lần seek và 3 ms.

Bài còn bàn vì sao cùng các file nhưng tar ra byte khác nhau; phần đó nằm trong bản gốc.

Đọc bài gốc

The author hand-built a tar archive from the POSIX spec using only Python's struct module and found that flipping one byte of a file's contents still extracts with exit code 0, while flipping one byte of the header makes tar refuse.

  • Structure: a sequence of 512-byte blocks. Each file gets a header block, then its contents padded to a multiple of 512, and the archive ends with two zero blocks. No magic number, no table of contents. Almost every number in the header is octal digits in ASCII. Two files came to 3,072 bytes and GNU tar 1.35 read it fine.
  • The checksum: a plain sum of the 512 header bytes, not a CRC or hash, and it covers only the header. Changing "first file" to "Xirst file" in the contents gave exit code 0 and a corrupted file on disk. Changing the first letter of the file name in the header gave "This does not look like a tar archive" and a failure status. The checksum exists so a tape drive could tell a header from data and resynchronise, not so you can trust the output. A bare .tar has no integrity guarantee; a .tar.gz is protected by gzip or xz, not by tar.
  • The octal limit: the size field holds eleven octal digits, max 8,589,934,591, one byte short of 8 GiB. For a sparse 9 GiB file, strict ustar refuses, the GNU format sets the top bit to switch to a binary integer, and pax writes an extra header with the size as unlimited decimal text.
  • No index: finding a file means walking forward header by header using each size field. With 2,000 files of 50 KB (about 100 MB), extracting the last one from an uncompressed tar took 2,001 seeks and 34 ms versus 7 seeks and 3 ms for ZIP.

The author built a grader that checks whether a quantum circuit written by an AI agent is the circuit it was asked for. - "Right on real answers" and "safe to gate on" are different claims. If an agent optimizes against the score, the adversarial result is the one that matters.

A test manager on pension projects in the Netherlands shares a set of in-browser generators that produce Dutch-looking test data which passes the system's checks without belonging to a real person.

The generators are also callable from an API and an MCP server, so a test can ask for a fresh valid BSN instead of reading one from a fixture file. One comment suggests adding phone numbers from ranges set aside by regulators for fictional use.

Ollama dành sẵn bộ nhớ cho toàn bộ context window dù cuộc trò chuyện dùng ít hơn nhiều, và có thể tốn thêm vài GB cho KV cache bên cạnh model đã tải. Vấn đề tương tự áp dụng cho llama.cpp và model GGUF chạy trong LM Studio.

  • Context length là dung lượng tối đa, gồm system prompt, lịch sử, input hiện tại và phần trả lời. Cấu hình 32K mà chỉ dùng 3K thì Ollama vẫn chuẩn bị cho mức lớn hơn.
  • Trên Apple Silicon, phần này lấy từ unified memory dùng chung với macOS; với GPU rời thì chiếm VRAM và có thể tràn sang bộ nhớ chậm hơn.
  • Mặc định của Ollama: 4K dưới 24 GiB, 32K từ 24 đến 48 GiB, 256K từ 48 GiB trở lên.
  • Chọn giới hạn từ số liệu thật: phản hồi của API có prompt_eval_count (token đầu vào) và eval_count (token sinh ra). Tác giả gợi ý thử 8K cho các cuộc trò chuyện vài nghìn token. Model reasoning sinh thêm thinking token nên cần tính cả phần này.
  • Cách đổi: slider trong app Ollama, /set parameter num_ctx 8192 trong terminal, hoặc PARAMETER num_ctx 8192 trong Modelfile. Hãy thử với hội thoại cần thông tin từ tin nhắn cũ; khi truncation bật, Ollama bỏ tin nhắn cũ nhưng giữ system message và tin mới nhất.
  • Ngoài ra có cache quantization: tuỳ chọn 8-bit (Q8) dùng khoảng một nửa bộ nhớ so với cache mặc định, đổi lại độ chính xác giảm nhẹ.

Đọc bài gốc

Ollama reserves memory for a model's full context window even when conversations use far less, and the KV cache can add several GB on top of the downloaded model. The same problem applies to llama.cpp and GGUF models running through LM Studio.

  • Context length is a maximum capacity covering the system prompt, history, current input and generated response. Configure 32K and use 3K, and Ollama still prepares for the larger limit.
  • On Apple Silicon the allocation comes from the unified memory shared with macOS; on a dedicated GPU it takes VRAM and can spill into slower memory.
  • Ollama defaults: 4K below 24 GiB, 32K between 24 and 48 GiB, 256K at 48 GiB or above.
  • Size it from real numbers: API responses include prompt_eval_count (input tokens) and eval_count (generated tokens). The author suggests testing 8K for conversations of a few thousand tokens. Reasoning models also produce thinking tokens, which must be budgeted.
  • To change it: the slider in the Ollama app, /set parameter num_ctx 8192 in a terminal session, or PARAMETER num_ctx 8192 in a Modelfile. Test with a conversation that needs earlier messages; with truncation enabled, Ollama drops older messages and keeps system messages and the latest one.
  • Cache quantization is another option: the 8-bit (Q8) setting uses roughly half the memory of the default cache, at slightly lower numerical precision.

Đọc bài gốc

The author built Sankh, a tiny request manager where every request is a .sh file holding a curl command, every test is a comment, and the UI is optional. The trigger was a pull request changing Petstore.postman_collection.json: a 1,400-line diff for one changed header, followed by a CI failure because the runner needed a different tool, login and environment copy.

Tests live in comments that the shell ignores, so each file still runs on its own with no lock-in:
- @name names the request and @tags assigns a suite (for example smoke).

- @capture TOKEN=.token saves a value for later requests; it can also read a header, as in REQUEST_ID=header X-Request-Id.
- Without an @expect status, any 2xx passes; with @expect status 404, a 404 is the success.

A collection is just a folder: sankh.toml (optional), .env.example, .env.local (gitignored, holds secrets), environments/dev.env and ci.env, and folders such as auth/ and pets/ whose numeric prefixes set the run order.
